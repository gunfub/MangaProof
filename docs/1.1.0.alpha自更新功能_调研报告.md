## 1. 结论摘要

### 1.1 可行性

需求整体**可实现**，且发布侧（产物命名、Release 流程、R2 域名、MirrorChyan 资源）已经就位，主程序侧需要从零新建 `mangaproof/update/`（当前完全不存在）：

| 需求环节 | 现状 | 结论 |
|---|---|---|
| 检查更新（MirrorChyan 无 CDK） | 服务端已上线，本地实测通过 | ✅ 直接可做 |
| 下载（R2 / GitHub / MirrorChyan） | R2 域名与 stable 资产已上线，实测可下载 | ✅ 直接可做 |
| 产物命名 `MangaProof-<version>-<os>-<arch>.<ext>` | 与需求 §22 完全一致 | ✅ 无需改打包 |
| 桌面替换 + 回滚 + 成功标记 | 无任何现成代码 | 🟡 新写，跨平台差异大 |
| PyInstaller onefile + Tkinter 安装器 | 打包链无安装器目标；**本机无 tkinter** | 🟡 新写 + 环境补齐 |
| R2 发布工作流 | 文件不存在 | 🟡 新写（有 MirrorChyan/Release 两个样板可抄） |
| Android 更新 | 打包链无 JNI 桥、无安装权限、清单无 FileProvider | 🔴 风险最高，见 §7.3 |

### 1.2 必须先决策的 5 个阻塞项（不解决无法开工）

1. **依赖安装授权**（规则 002 强制）：`httpx`（需求 §8 指定）与 `keyring`（需求 §14 指定）均不在 `uv.lock` 中，必须 `uv add`。**等你批准后才动手**，详见 §4。
2. **安装器如何交付到用户机器**：需求 §51 的更新包结构与 §74 的 R2 清单里**都没有安装器二进制的位置**——这是需求最大的空白。**已决策**：安装器随主程序 onedir 一起构建、一起发布，与主程序可执行文件**同级同目录**，更新时复制到临时目录执行。歧义分析与 PyInstaller 落地写法见 **§11.3**。
3. **Android 第一版是否实现**：需要在 Android 打包链新增 `REQUEST_INSTALL_PACKAGES` + FileProvider + JNI 调用系统安装器（当前仓库零 JNI 依赖，且曾明确放弃过 Java 原生桥）。见 §7.3。
4. **settings.json 结构**：需求 §13 建议嵌套 `"update": {...}`，而现有 `settings.json` 是**扁平结构且 save() 白名单化**（未列入的键会被丢弃）。见 §6.1。
5. **"更新"入口位置**：需求 §10 写「顶栏 关于 → 更新」，但现有「关于 MangaProof」是 `QMessageBox.about`（不是菜单也不是对话框），且菜单结构被测试逐字断言。见 §6.2。

### 1.3 关键风险 Top 6

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | Android CI 有 `--fail-on-unknown` 硬门槛：新增任何运行时依赖若没有 p4a recipe 归宿，**Android 构建直接失败** | 加了 httpx 就红 | 补本地 recipe + 白名单；keyring 走"不打包"白名单。见 §4.2 |
| R2 | macOS `.app` 用 Python `zipfile` 解压会**丢失符号链接与执行位**（`.app` 依赖 `Frameworks/`↔`Resources/` 交叉软链）→ codesign 失败/无法启动 | 更新后应用打不开 | 用 `/usr/bin/ditto -x -k` 解压，或按 `external_attr >> 16` 自实现还原。见 §5.3 |
| R3 | macOS 产物仅 ad-hoc 签名、**不公证**；替换后 Gatekeeper 可能拦"已损坏" | 更新后无法启动 | 发布侧上 Developer ID + 公证 + staple；否则至少 `xattr -dr com.apple.quarantine`。见 §5.3 |

| R6 | 需求 §57 的"旧数据成功加载"目前**没有可用的公开判据**（`RecentManager._usable` 是私有），且程序完全没有命令行参数解析 | 成功标记写不准 → 误回滚 | 新增启动自检函数 + `--update-token/--success-marker` 参数解析。见 §6.3 |

## 3. 外部接口实测（第一手）

### 3.1 MirrorChyan 【实测 + 官方文档】

**官方集成指南**：`https://github.com/MirrorChyan/docs`（README.md）与 OpenAPI 文档 <https://apifox.com/apidoc/shared-ffdc8453-597d-4ba6-bd3c-5e375c10c789/253583257e0>；错误码表 `ErrorCode.md`。

检查更新接口（**不带 CDK**，直连可用，未使用代理）：

```http
GET https://mirrorchyan.com/api/resources/MangaProof/latest?os=linux&arch=x64&channel=stable
```

实测响应（2026-09-22 本机）：

```json
{"code":0,"msg":"current resource latest version is v1.0.0",
 "data":{"version_name":"v1.0.0","version_number":2,"channel":"stable",
         "os":"linux","arch":"amd64","release_note":""}}
```

**已验证的行为**

| 项 | 实测结果 |
|---|---|
| 检查是否需要 CDK | **不需要**（需求 §17 正确） |
| 响应字段 | `code` / `msg` / `data{version_name, version_number, channel, os, arch, release_note}`；**不含** `url`/`sha256`/`filesize`/`update_type`（那些只在带 CDK 的下载信息请求里返回，与 §19 一致） |
| `os` 取值 | `windows` 与 `win` **都接受**，回显统一为 `windows`；`macos` → 回显 `darwin`；`linux` → `linux`；`android` → `android` |
| `arch` 取值 | `x64` → 回显 `amd64`；`arm64`/`aarch64` → 回显 `arm64` |
| `channel` 缺省 | 缺省即 `stable` |
| 非法参数错误码 | `8001` resource not found；`8002` invalid os；`8003` invalid arch；`8004` invalid channel；`7002` invalid cdkey |
| 带 `cdk` 的**检查**请求 | 非法 CDK 会**直接报错 7002**（即使只是查询）→ 印证 §17「检查阶段不得携带 CDK」是必须的 |
| `current_version` 参数 | 本部署接受但不改变响应内容（未返回 `update_type`） |
| Android 资源 | `rid=MangaProof_exec&os=android&arch=aarch64` **可用**，返回 `os=android, arch=arm64`（§18/§65 可行） |
| HTTP 状态 | 业务错误也返回 HTTP 200 + body 里的 `code`，客户端**必须解析 body** |

补充实测（**下载信息接口的降级行为**，用无效 CDK 探测）：

| 请求 | 结果 |
|---|---|
| `...&cdk=&user_agent=MangaProofUpgrade`（**CDK 为空串**） | `code:0`，返回的是**检查类数据**（无 `url`/`sha256`/`filesize`）→ **空 CDK 等同于不带 CDK**，客户端必须在发请求前就把"CDK 为空"判为错误，否则会静默拿到一份没有下载地址的响应 |
| `...&cdk=TESTINVALID&user_agent=MangaProofUpgrade` | `code:7002` invalid cdkey，`data` 里仍带版本信息但**无下载字段** |
| `MangaProof_exec ... &cdk=TESTINVALID&user_agent=MangaProof_exec` | 同样 `code:7002`（Android rid 与 `user_agent=MangaProof_exec` 路径存在且可达） |
| 有效 CDK 的成功响应（`url`/`sha256`/`filesize`/`update_type` 的确切形状） | **已由 OpenAPI 文档确认【文档】**，见下表 |

带有效 CDK 时的成功响应字段（官方 OpenAPI「成功示例」，与需求 §19 完全一致）：

```json
{
  "version_name": "v1.1.0",
  "version_number": 2,
  "url": "https://mirrorchyan.com/api/resources/download/xxxxxx",
  "filesize": 9812344,
  "sha256": "11451419198100abcd",
  "update_type": "full",
  "arch": "x64",
  "channel": "stable",
  "release_note": "## v1.1.0\n- 更新了 xxx - 修复了 xxx"
}
```

→ `url` 由服务端下发（**客户端不得自行拼接**，§19 得到官方印证）、`sha256` 可直接用于校验、`filesize` 可用于下载前显示大小、`update_type` 本需求只用 `full`（§1 不做增量）。

**带 CDK 的真实响应（2026-09-22 由需求方实测提供，CDK 已按 §16 脱敏，本报告不记录其值）**：

```json
{"code":0,"msg":"success","data":{
  "version_name":"v1.0.0",
  "version_number":2,
  "url":"https://mirrorchyan.com/api/resources/download/3JfzDTSxLwQjzxboaReYmeqoEf5",
  "sha256":"10f9a0931a4c04b18ca94672f5b46912ac86bbcb70e88e9502ef1ce227e8a364",
  "channel":"stable","os":"android","arch":"arm64",
  "update_type":"full","release_note":"",
  "filesize":176652385,
  "cdk_expired_time": "…"}}
```

由此**新增确认**的四点（都会影响实现）：

| 观察 | 对实现的影响 |
|---|---|
| 响应字段比官方示例**多一个 `cdk_expired_time`** | 可用于 UI 提示"CDK 有效期至 …"；解析时按可选字段处理（缺失不得报错） |
| `url` 形如 `https://mirrorchyan.com/api/resources/download/<token>` | **典型短效地址**，禁止落盘/写配置/自行拼接（§21）；每次"立即更新"都要重新请求 |
| `filesize = 176652385` 与 R2 上 `stable/MangaProof-1.0.0-android-aarch64.apk` 的实测字节数**完全相同** | 强证据：MirrorChyan 与 R2 分发的是**同一个构建产物** → manifest 里的 SHA-256 与 MirrorChyan 返回的 `sha256` 应当一致，可作为交叉校验 |
| 该请求用的是 `user_agent=MangaProofUpgrade`（而非 `MangaProof_exec`）且成功 | `user_agent` **未见严格校验**；但实现仍按需求写死：桌面 `MangaProofUpgrade`、Android `MangaProof_exec`，不做"反正不校验"的偷懒 |
| 带 CDK 的请求即使只有信息查询也返回 `sha256` | **下载前**即可拿到官方校验值，不必等下载完再比对；§53 的"更新前最终校验"因此可提前到下载开始时 |


> 结论：**错误分支必须先判 `code != 0`，再判"下载字段是否齐全"**；两种失败要给出不同的用户提示（CDK 无效 / 该版本暂无下载包）。

**官方集成流程与需求 §28 的关系【文档】**（官方流程图原文）：检查更新一律调用 MirrorChyan（官方明确"推荐即使未填写 CDK 时也使用 Mirror酱 API 检查"）→ 版本比对 → 有更新时看返回里**有没有 `url`**：有 `url` 就用它下载，**没有 `url` 就改走 GitHub 下载**。

> ⚠️ **本项目对该流程做了明确简化（需求方 2026-09-22 确认）**：**检查阶段统一使用无 CDK 格式**，因此检查响应里**永远没有 `url`** → 官方流程中"有 url 就用它下载"这一分支**在本项目不会触发**。
> 取而代之的是需求 §28 的渠道矩阵：**下载源由用户选择的渠道决定**；若渠道为 MirrorChyan，则在"立即更新"阶段**重新**发起一次带 CDK 的请求来换 `url`（见 §11.8）。
> 这样做的收益：检查链路零凭据、可无 CDK 使用、与官方"无 CDK 也能检查"的建议一致；代价：检查阶段拿不到 `url`/`sha256`/`filesize`（见 §11.8 的补齐方式）。


另外三条官方原文对实现有直接约束【文档】：
- "请考虑日志、配置文件等中，尽量不要出现 CDK 明文，避免意外泄漏" → 对应需求 §16（我们再加一层 keyring 存储）。
- "若待更新程序本身正在运行，可先将其重命名，再下次启动再删除。即**重命名是不依赖程序是否未被占用的**" → 官方认可 `.old` 改名方案。
- 官方有 `changes.json` 增量包机制；需求 §1 明确**不做增量**，忽略即可。

**发现的数据问题（需你处理）**：`channel=alpha` 返回 `version_name":"alpha"`（**不是** `v1.1.0.alpha`，无法解析成版本号）；`channel=beta` 返回的是 `v1.0.0`（stable 的版本）。这说明 MirrorChyan 上 alpha 通道的资源是用 `version_name=alpha` 上传的。后果：客户端在 alpha 通道做"目标版本 > 当前版本"比较时会得到非法版本串。**建议**：要么在 MirrorChyan 侧修正该资源，要么客户端对无法解析的 `version_name` 明确提示"该通道版本信息异常"而不是静默判定"无更新"。

## 5. 跨平台安装器工程要点

### 5.1 Windows

- 提权必须用 `ShellExecuteExW` + `"runas"` + `SEE_MASK_NOCLOSEPROCESS|SEE_MASK_NOASYNC`（`ShellExecuteW` 拿不到进程句柄、也拿不到准确错误）；`GetLastError()==1223` 表示用户在 UAC 取消（不重试、不降级）；调用前需 `CoInitializeEx`。【文档】
- 等待旧进程退出：`OpenProcess(SYNCHRONIZE|PROCESS_QUERY_LIMITED_INFORMATION)` + `WaitForSingleObject`（`ERROR_INVALID_PARAMETER` = 进程已不存在）。【文档】
- 「运行中的 exe 可改名、不能直接删除/覆盖」有官方旁证 → 先 `rename` 再解压的方案成立；删除 `.old` 失败可用 `MoveFileExW(..., MOVEFILE_DELAY_UNTIL_REBOOT)` 兜底（需管理员）。【文档】
- **R4 风险**：PyInstaller 6.22.1+ 给 onefile 加了父进程校验，6.22.3 起对"UAC 提权 + 继承非提权用户环境变量"的进程强制生效 → 提权启动安装器前**清理 `_PYI_*` 环境变量**或设 `PYINSTALLER_RESET_ENVIRONMENT=1`，并在 CI/真机验证。【文档 + 待验证】
- 提权安装器用 `CreateProcess` 拉起的新版会**继承管理员完整性级别** → 最优解是安装目录本身用户可写（无需提权）；否则应由非提权一侧（主程序/安装器非提权实例）启动新版。【文档】

### 5.2 Linux

- 提权降级链（社区成熟做法，Tauri updater 同款）：`pkexec`（**只跑 CLI 安装逻辑**，绝对路径，`--disable-internal-agent`）→ `sudo -A` + `SUDO_ASKPASS=<zenity|kdialog|ssh-askpass>` → 提示用户"复制命令到终端执行"。**返回码：`126` = 用户取消（停止降级）；`127` = 机制不可用（才降级）**。`pkexec` 默认会清洗 `DISPLAY`/`XAUTHORITY`，不能用来启动 GUI。【文档】
- `tarfile.extractall(filter="data")` **同时**满足"防路径穿越/设备文件/越界链接"与"**保留 exec 位**"；Python 3.12 默认仍是 `fully_trusted`（仅 DeprecationWarning）→ **必须显式传 `filter="data"`**。【文档 + 本机实测 `tarfile.extraction_filter is None`】
- 安装目录 `rename` 对运行中可执行是安全的（POSIX 只改目录项）；删 `.old` 时若旧进程还在会失败 → 要重试 + 明确报错，不要静默忽略。【文档】
- 建议安装器支持 `--cli` 模式：无图形会话（SSH/无 Tk）时唯一可用的兜底路径。【文档】

### 5.3 macOS

- **R2 风险（最高）**：Python `zipfile` **不还原符号链接、不还原 Unix 权限位**（`external_attr` 完全不被使用）。PyInstaller 的 `.app` 依赖 `Contents/Frameworks` ↔ `Contents/Resources` 的交叉软链 → 用 `zipfile.extractall` 解 `.app` 会得到"内容为链接路径的普通文件"，导致 `codesign` 失败/"bundle format is ambiguous"/启动即崩。
  **对策（三选一，建议 a）**：a) 用系统自带 `/usr/bin/ditto -x -k archive.zip dest` 解压；b) 自实现 zip 解压：按 `(zi.external_attr >> 16) & 0xFFFF` 取 mode、`stat.S_IFLNK` 时 `os.symlink(zf.read(zi).decode())`、普通文件 `os.chmod(out, perm)`；c) macOS 更新包改用 tar.gz（`filter="data"` 天然保留 exec 与软链）。【文档】
- 提权：`osascript -e 'do shell script "..." with administrator privileges'`；用户取消 → 返回 `-128` / stderr `User canceled.`。**提权只做文件操作（mv/rm/xattr），启动新版用非提权的 `open -n -a`**。【文档】
- **`open` 的 pid 不是 app 的 pid**【实测，2026-09-24】：`open -n -a` 把启动请求交给
  LaunchServices 后**立即退出**（不带 `-W` 时不等应用退出），app 由 launchd 拉起、
  pid 完全不同，而且两者没有父子关系。所以安装器**绝不能**把 `subprocess.Popen`
  拿到的 pid 当作"新版进程"来跟踪 —— 真机上表现为每次更新都秒判"新版已退出但没有
  写入成功标记"并回滚（回滚还会删掉正在启动的新版目录）。正确做法：pid 消失后按
  **进程名**找回主程序（`ps -A -o pid=[,state=],comm=`，macOS 的 comm 是完整路径、
  Linux 是进程名，统一取 basename；僵尸要剔除），换成它的 pid 继续等 marker。
- **R3 风险**：当前 `.app` 只有 ad-hoc 签名、无 Developer ID、无公证（`packaging/main_macos.spec:65,85-98`）。替换后首次启动可能被 Gatekeeper 拦。建议：替换后 `xattr -dr com.apple.quarantine`（**不要用 `-c`**）+ `codesign --verify --strict`；根治要在发布侧上签名+公证+staple。【文档】
- marker 传递不要依赖 `open --args`（会被已存在的实例吃掉）→ 用"约定路径 + token 内容校验"。【待验证】

### 5.4 通用（与需求 §57~§64 对应）

- **marker 必须校验 `version + token`**，不能只判"文件存在"（上一次更新的残留 marker 会导致误判成功，不幂等）。【文档】
- **状态文件放用户数据目录，不要只放临时目录**：`/tmp` 与 `%TEMP%` 可能被系统清理/重启清空，会导致断电后无法判断"更新未完成"。需求 §58 把 marker 放临时目录是合理的（它是"本次更新"的信号），但**安装器的阶段状态**建议另存一份到程序目录旁的持久位置。【文档】
- 分层超时优于"单层 60 秒"：等新进程出现 10~15s、等 marker 60~120s；"marker 未出现 **且** 新进程已消失" → 立即回滚（不要等满 60s，这正是需求 §60）。【已实现，2026-09-24】
  落地参数：``RELOCATE_TIMEOUT = 20s``（等新进程出现的宽限期）、``SUCCESS_TIMEOUT = 60s``
  （等 marker 的上限）、``LOOKUP_INTERVAL = 0.5s``（按进程名查询的节流）。
  **"新进程已消失"的判据是"按进程名找不到主程序"，不是"跟踪的 pid 消失"**（见 §5.3 的
  `open` 语义）；查不了进程时按"可能还活着"处理，等满 60s 再超时，绝不早判失败。
  等待期间不结束主程序，只有超时才结束它并回滚（需求方 2026-09-24 决策）。
- 复制/恢复用户数据用"临时名 + `os.replace`"保证幂等；备份目录名带 version+token 避免覆盖上一次的备份。【文档】
- 安装器日志写**持久目录**（否则安装器被杀时无任何线索）。【文档】

未定义项：R2 的三条 secret **键名**（建议 `R2_ACCOUNT_ID` / `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY`，bucket 与 endpoint 用 `env` 常量）。

**上传工具已核实【实测】**：`ubuntu-24.04` runner 镜像**预装 AWS CLI v2（2.36.40）**与 curl，**不含 rclone/wrangler**（`actions/runner-images` 的 `images/ubuntu/Ubuntu2404-Readme.md:107-108`）→ 直接用
`aws s3 cp --endpoint-url https://$R2_ACCOUNT_ID.r2.cloudflarestorage.com`（`--cache-control no-store` 可一并设置 manifest 的缓存头）即可，无需额外安装步骤；清空 channel 用 `aws s3 rm s3://$R2_BUCKET/{channel}/ --recursive`（严格限定前缀）。

> **GitHub `digest` 格式已核实【文档】**：官方 REST 文档（`docs.github.com/en/rest/releases/assets`）的 Asset schema 中 `digest` 是**必填字段**（`"required":[...,"digest",...]`，类型 `["string","null"]`），示例值为
> `"digest": "sha256:2151b604e3429bff440b9fbc03eb3617bc2603cda96c95b9bb05277f9ddba255"`
> → **带 `sha256:` 前缀**，生成 manifest（§26 要求裸 hex）时必须 `split(":", 1)[1]`；`digest == null` 时按 §27 直接让 workflow 失败。
> 另：本机匿名 API 实测被限流（403 `API rate limit exceeded`），说明 CI 里应始终用 `GITHUB_TOKEN` 认证调用（5000 次/小时）。

### 7.2 安装器构建（需求 §43/§44）

- 新增独立 spec（如 `packaging/installer.spec` / 平台各一份）：onefile（不写 `COLLECT`、`EXE(..., exclude_binaries=False)`）、`console=False`、**不 exclude tkinter**、`upx=False`（沿用仓库惯例）
- 安装器随主程序发布：三份 `main_*.spec` 各追加一条 `("MangaProof-update-installer", 路径, "EXECUTABLE")` 的 COLLECT 条目（**不能用 `binaries=`**，否则会落进 `_internal/`）——完整依据见 **§11.3**
- 挂在 `build.yml` 现有 5 个桌面矩阵（`build.yml:43-52`、`113-122`）上构建；产物命名要**避免被 release.yml 的 `MangaProof-*` 前缀误收**（`release.yml:195,233` 会命中 `MangaProof-update-installer-*`）→ 建议用 `MangaUpdater-*` 或不以 `MangaProof-` 开头的 artifact 名
- **本机无 tkinter**（系统 `python3` 与 `.venv` 均 `ModuleNotFoundError: No module named 'tkinter'`）→ 本地无法验证安装器 GUI；CI runner 是否带 Tk **【待验证】**，建议 workflow 加一步 `python -c "import tkinter"` 显式卡口
- 分发方式（**待你决策**，需求未定义）：推荐"随主程序 onedir 一起分发，更新时复制到 TEMP/CACHE 执行"

### 7.3 Android 更新（需求 §65/§66）—— 风险最高

现状：Android 打包链**没有任何 JNI 桥**（唯一 Java 是 `packaging/android/java/com/mangaproof/a11y/A11yEnvProvider.java`，一个注入环境变量的 ContentProvider），清单权限只有 `MANAGE_EXTERNAL_STORAGE`（`scripts/android/build_android.py:335-337`），且 `mangaproof/storage/picker.py` 的模块注释明确记录了"放弃自建 Java 原生桥"的历史决定。

需求 §65 要"写入系统 Download + 调用系统安装器"，这意味着需要：
1. `android.permission.REQUEST_INSTALL_PACKAGES`（Android 8+ 必须）+ 用户授予"安装未知应用"；
2. 通过 **FileProvider** 把 APK 暴露给系统安装器（`file://` URI 在 Android 7+ 会触发 `FileUriExposedException`）——需在 `packaging/android/p4a_hook.py` 的清单注入逻辑里追加 provider + `res/xml/file_paths.xml`；
3. **JNI 调用**（p4a 的 `android`/pyjnius 模块）发 `Intent.ACTION_VIEW` + `application/vnd.android.package-archive`；
4. APK 必须与已安装应用**同签名**（CI 已用仓库 keystore 重签，✅ 前提满足，但 fork 构建的 `-unsigned.apk` 无法安装）。

这属于"新增 Android 构建期依赖 + 清单变更 + 未验证的 JNI 路径"，建议**单独作为一个阶段**，或第一版先隐藏 Android 更新入口。

**§83「无法直接启动」提示窗（2026-09-25 追加、同日改版）**：该提示窗**按上表的调色板与版式做**（`updater/ui.py:_show_dark_notice()`）—— 主背景/正文/次要/警告/按钮五档色值、随包 MiSans、主按钮右下角、Esc/回车/关窗同义，**没有例外**。第一版曾用系统原生 `messagebox`（理由是想让人一眼分辨"这不是更新进度窗口"），实测观感与安装器主窗口割裂、太像系统报错框，故改为"主窗口的缩小版"；原生 `messagebox` 只保留为深色窗建不起来时的第二级降级，第三级是 stderr + 日志。

**内置字体的落地方式（2026-09-25 追加）**：`packaging/installer.spec` 的 `datas` 随包 `font/MiSans-Medium.ttf`，运行时由 `updater/fonts.py` 按平台注册进**本进程**（Windows `AddFontResourceExW(FR_PRIVATE)`、Linux `FcConfigAppFontAddFile(FcConfigGetCurrent(), …)`、macOS `CTFontManagerRegisterFontsForURL(…, Process)`），**不写系统字体目录**（安装器是一次性程序，改用户环境没必要）。两个实测要点：① Tk 看到的家族名按平台不同 —— GDI 用 name 表 nameID1（`MiSans Medium`），CoreText / fontconfig 用 nameID16（`MiSans`），所以候选名两个都要试；② Linux 的 Xft/fontconfig **不做合成粗体**（bold 请求仍匹配回 Medium），只带 Medium 时三个粗体标签会退化为 Medium（Windows / macOS 由 GDI / CoreText 合成，观感不变）—— 这是「只随包一份 Medium」的已知代价。Tk built without Xft 时注册成功也看不到该家族，`updater/fonts.py` 会核对 Tk 家族表后回退系统链。

### 11.3 【规格】安装器与主程序的发布层级（消除歧义）

**歧义本身**：「放在一起」可读作 ①同一目录，或 ②同一发布包但不同层级。

**判定依据（全部来自需求自身条文）**：

- §38：Windows/Linux 的**安装目录 = `sys.executable` 所在目录**（例：`~/example/MangaProof/`），父目录是 `~/example`。
- §54：替换的是**整个安装目录**——`~/example/MangaProof` → `MangaProof.old`，再把新 `MangaProof/` 解压到 `~/example/`。
- §40：安装器**必须从临时目录运行**，不得直接从旧程序目录运行。
- §61：成功后的清理清单是 `.old / 数据备份 / 更新包 / 安装器临时目录 / marker`——**没有**"清理安装器的持久位置"这一项。
- §47/§49：用户数据白名单是从**程序目录**（= 安装目录）复制。

**唯一化结论 → 解读 ①（同一发布包、且与主程序可执行文件同级）**：

- 若取解读 ②（安装器与 `MangaProof/` 平级，落在**父目录**），则安装器处于应用不拥有、且真实场景中常为共享/受保护目录的位置（`C:\Program Files\`、`/opt`、`/Applications`），且 §61 没有任何清理它的语义 → **会产生"永久滞留的旧安装器"**，与 §61 不闭合。
- 取解读 ① 时：安装器随安装目录整体被 `.old` 替换，新旧天然同版本；运行时按 §40 先复制到 TEMP，**运行中的副本不受替换影响**；§61 只需删掉 TEMP 副本，持久位置由新包自带 → 与 §38/§40/§47/§49/§54/§61 **全部自洽**。

**固化后的发布结构（§51 的图示需按此补正）**：

```text
Windows（zip 内顶层为 MangaProof/）
MangaProof/
├── MangaProof.exe
├── MangaProof-update-installer.exe      ← 与主程序可执行文件同级
└── _internal/                            ← PyInstaller 6 onedir 实际布局，§51 原图漏画

Linux（tar.gz 内顶层为 MangaProof/）
MangaProof/
├── MangaProof
├── MangaProof-update-installer
└── _internal/

macOS（zip 内顶层为 MangaProof.app/）
MangaProof.app/
└── Contents/
    └── MacOS/
        ├── MangaProof
        └── MangaProof-update-installer
```

**落地方式（PyInstaller，已核对本机 6.x 源码，结论与直觉相反，务必按此写）**：

**不能**走 `Analysis(binaries=[("安装器", ".")])`／把安装器塞进 `a.binaries`：

- `PyInstaller/building/api.py` 的 `COLLECT.assemble()` 里，**只有** `typecode in ("EXECUTABLE", "PKG")` 的条目才落在 `dist/MangaProof/` 根目录；其余（含 `BINARY`）一律落进 `contents_directory`（即 `_internal/`）→ 与"和主程序可执行文件同级"不符；
- 在 macOS 上 `BINARY` 还会被 BUNDLE 归到 `Contents/Frameworks`（`osx.py` 的分类规则），同样不满足"同级"。

**正确做法**：给 `COLLECT` 追加一条**裸 TOC 三元组，typecode 用 `'EXECUTABLE'`**：

```python
INSTALLER_FILENAME = "MangaProof-update-installer"        # Windows 加 .exe
COLLECT(
    exe, a.binaries, a.datas,
    [(INSTALLER_FILENAME, str(installer_path), "EXECUTABLE")],   # (dest_name, src_name, typecode)
    strip=False, upx=False, upx_exclude=[], name="MangaProof",
)
```

源码依据（本机 `.venv` PyInstaller 6.x）：

| 行为 | 出处 | 结论 |
|---|---|---|
| `EXECUTABLE` 落 `dist 根`，其余落 `_internal/` | `building/api.py` `COLLECT.assemble()`：`if typecode in ("EXECUTABLE","PKG"): dest_path = join(self.name, dest_name)` | Windows/Linux 与主程序 exe **同目录** ✔ |
| `EXECUTABLE` 会被 `chmod 0o755` | 同函数结尾：`if typecode in ('EXTENSION','BINARY','EXECUTABLE') …: os.chmod(dest_path, 0o755)` | Linux/macOS 可执行位自动保留，无需额外 chmod ✔ |
| macOS：所有 `EXECUTABLE` 条目进 `Contents/MacOS` | `building/osx.py` 注释原文 "All entries with EXECUTABLE are placed in `Contents/MacOS` directory." | `MangaProof.app/Contents/MacOS/` ✔ |
| 安装器缺失/不是文件即报错 | `COLLECT.assemble()`：`if not os.path.isfile(src_name): raise ValueError` | 天然满足"构建期强校验"，不会静默出包 ✔ |

三份 `main_*.spec` 各自声明（符合需求 §7「按平台显式声明」），安装器路径由 CI 传入（环境变量或固定约定路径），**读不到就构建失败**。

**CI 构建顺序**：`构建安装器（5 个桌面目标）→ 再构建主程序（spec 读不到安装器即失败）`——不能反序，也不允许"安装器缺失时静默出包"。

**连带的规格补正**：
- §51「包结构异常不进替换流程」的校验必须**同时接受 `_internal/`**，否则更新全流程会 100% 卡在结构校验（§2 的 R5）。
- 更新包体积会因随包安装器增加（onefile + Tk ≈ 十 MB 量级，**待实测**，见 §10.10）。

### 11.4 【规格】安装器进度 UI 必须显示"具体文件操作"

**进度模型（安装器内核 → UI 的事件契约）**：

```text
on_phase(phase_key)                  # INIT/VALIDATE/BACKUP_DATA/VERIFY_PACKAGE/RENAME_OLD/
                                     # EXTRACT/RESTORE_DATA/LAUNCH_NEW/WAIT_SUCCESS/CLEANUP/ROLLBACK
on_item(rel_path)                    # 当前正在处理的具体文件或目录（相对路径）
on_progress(done, total)             # 当前阶段内的条目计数（total 未知时发 -1）
on_log(line)                         # 追加到明细区（可选，同 on_item 内容）
```

**UI 必须同时呈现三层信息**（缺一不可）：

```text
正在恢复用户数据…                          3/12

正在复制：logs/2026-09-22.log

[██████████░░░░░░░░░░]  50%
```

1. **阶段**（中文可读文案，对应 `on_phase`）；
2. **当前具体文件操作**（`on_item`，例如 `settings.json`、`recent.json`、`logs/2026-09-22.log`、`MangaProof.old → MangaProof`、`解压 MangaProof/_internal/PySide6/Qt/...`）；
3. **进度条 + 计数**。

细则：解压阶段可按"已解压条目数"驱动进度；数据恢复/备份阶段按白名单条目数驱动；改名/启动/等待阶段为不确定进度但**仍要显示具体动作**（如"等待新版本写入成功标记（最长 60 秒）"）；失败时明细区保留最后一条操作，便于用户截图反馈。

  （§65 / §66），按需求方决策留待 Android 分支统一处理。

### 11.8 【规格】检查与下载两阶段的请求规格（凭据边界）

> 需求方 2026-09-22 明确：**检查有无更新统一使用无 CDK 格式；下载更新必须附带 CDK**。为降低复杂度，不做任何"带 CDK 的检查"变体。

**A. 检查阶段（零凭据）**

```text
请求 = §11.5 的 7 条地址之一（channel 动态替换）
不得追加 cdk
不得追加 user_agent
不追加 current_version（版本比较在本地做，见下）
```

| 项 | 规定 |
|---|---|
| 携带参数 | 仅 `os` / `arch` / `channel` |
| 响应可用字段 | `version_name`（**唯一**参与版本比较）、`release_note`（"有更新"页展示）、`version_number`（仅展示/日志，**不参与比较**）、`channel`/`os`/`arch`（仅日志核对） |
| 响应**没有**的字段 | `url` / `sha256` / `filesize` / `update_type` / `cdk_expired_time` |
| **结构性保证（写进代码，不靠自觉）** | 检查函数签名**不得包含 cdk 形参**（如 `check_latest(*, branch, os_name, arch)`），从类型层面杜绝误传；并加单测断言构造出的 URL **不含** `cdk` 与 `user_agent` 子串 |
| 失败提示 | `8001` → "当前系统架构暂不支持更新"；网络失败 → 可重试提示（检查为只读，重试无副作用） |

**B. 下载阶段（必须带 CDK，且仅在用户点击「立即更新」之后）**

| 渠道 | 请求 | 校验值来源 |
|---|---|---|
| MirrorChyan | **同一地址**追加 `&cdk=<CDK>&user_agent=<桌面 MangaProofUpgrade / Android MangaProof_exec>` → 取 `url`（服务端短效地址，不得自行拼接）、`sha256`、`filesize`、`update_type` | 响应里的 `sha256`（**下载前即可拿到**） |
| Cloudflare R2 | `https://download.mangaproof.priloba.com/{channel}/MangaProof-<version>-<os>-<arch>.<ext>` | `{channel}/MangaProof-<version>-sha256.json` 中该文件名的值 |
| GitHub | 按文件名在目标 Release 的 assets 中查找后下载（文件名需 URL 编码） | asset 的 `digest`（`sha256:<hex>`，剥前缀） |

- **CDK 为空时不得发 MirrorChyan 下载请求**（实测：`cdk=` 空串会退化成"检查类响应"，静默丢失下载字段）→ 直接提示"MirrorChyan 渠道需要 CDK，请填写或改用 R2/GitHub"。
- R2 / GitHub 渠道**不使用** CDK；MirrorChyan 渠道**不使用**代理与限速（需求 §28/§29/§30）。
- GitHub 渠道的匿名 API 可能被限流（实测 403）→ 需把 403/429 明确转成"GitHub 暂时不可用，可改用 R2/MirrorChyan"。

**C. 简化带来的一个后果，及其补齐方式**

因为检查请求不带 CDK，**"发现新版本"页面拿不到 `filesize`**，而需求 §33 要求显示"文件 / 大小"：

| 渠道 | 文件名 | 大小 |
|---|---|---|
| R2 | 本地按 `版本/os/arch` 推断（命名规则见 §11.5） | 对目标对象发一次 **HEAD**（带 cache-bust）取 `content-length` |
| GitHub | 同上 | Release API 的 asset `size`（或对 `browser_download_url` 发 HEAD 并跟随重定向） |
| MirrorChyan | 需带 CDK 的响应才知道 `url`，而 `url` 不含文件名 | **不预取**：在"发现新版本"页显示"点击「立即更新」后获取"，点击后再把 `filesize` 补显到下载界面（保证"只有立即更新才用 CDK"这条不被破坏） |

> 实现提示：§33 的"大小"在 R2/GitHub 渠道必须在**点击立即更新之前**取到；若 HEAD 失败（无网/CDN 异常），降级显示"—"，**不得因此阻断更新流程**。

### 11.9 【规格】R2 发布流程的强顺序与硬条件（2.1 / 2.4 固化）

```text
① 触发与守卫
   · release 事件（release.edited）+ workflow_dispatch(tag) 兜底
   · 硬条件 A：github.event.release.prerelease == false      ← 跳过预发行
   · 硬条件 B：目标 commit 上的 Desktop Build 与 Android Build 均为最新一次 success
                （与 MirrorChyan 发布同款检查，复用 release.yml:93-189）
② 上传前完整性检查（任一失败 → 立即退出，绝不动 R2）
   · Release 存在、tag 与 __version__ 一致、commit 正确
   · 7 个资产齐全、文件名符合 MangaProof-<version>-<os>-<arch>.<ext>
   · 每个 asset 的 digest 非空；格式 sha256:<hex> → 生成 manifest 时剥前缀
   · 生成 MangaProof-<version>-sha256.json（文件名动态，不硬编码）
③ 清空目标 channel
   · 严格限定 {channel}/ 前缀（stable → 只删 stable/*）
   · alpha/、beta/ 一律不动
④ 上传
   · {channel}/ 下 7 个资产 + manifest；manifest 显式设 Cache-Control: no-store
⑤ 上传后复验（不能只看上传命令退出码）
   · 带 cache-bust 查询串 HTTP 校验：7 个资产 + manifest 均可访问
⑥ 可选交叉校验（发布后人工/人工触发，不进自动流程）
   · 用一条 CDK 请求 MirrorChyan 下载信息，断言其 sha256 == manifest 中同文件名的值
     （依据：MirrorChyan 的 android-aarch64 资产 filesize 与 R2 同资产完全相同，见 §3.1）
   · 不把 CDK 放进 CI secrets 之外的地方；该步骤默认关闭
```
