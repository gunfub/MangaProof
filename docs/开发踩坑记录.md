# MangaProof 开发踩坑记录

按主题累计「踩过一次就别再踩」的经验，新条目追加在文末，编号顺延。

每条固定四段：**症状 → 成因 → 定位手法 → 规则**。写清楚"当时是怎么发现的"，
比只写结论更有用 —— 下次症状不一样时，定位手法才是能直接复用的那部分。

---

## 1. 未 patch 的模态对话框会把 offscreen GUI 测试永久卡死

**症状**：pytest 跑到某个 GUI 用例就没有任何输出、也不报错，一直挂着不结束；
用 `| tail` 之类管道时更惨 —— 连"卡在哪个用例"都看不到（管道缓冲会把日志全
藏起来，直到进程退出）。

**真实案例**（2026-10-08，返修单选项窗口那次改动）：
`tests/test_gui_smoke.py::test_report_options_switch_controls_dialog` 第 ① 段
直接调 `window.generate_report_dialog()` 出报告，只 patch 了
`ReportDialog.exec`，**漏了 `QMessageBox.information`**。报告生成完成后
`MainWindow._on_report_finished()` 会弹「已生成：<路径>」信息框
（`mangaproof/ui/main_window.py`），而测试这边正卡在 `_wait_for_report()` 的
`app.processEvents()` 里等后台线程收尾 —— 事件循环一进模态框就再也出不来。

**成因**：`QMessageBox.information / warning / critical` 是静态方法，内部自带
事件循环并阻塞调用方；`app.processEvents()` 推不动它，offscreen 平台又没有真人
去点「确定」，于是死等。注意这个坑是**成对**的：被测代码弹框（正常功能）+
测试没 patch（遗漏），两边都没错，合起来才卡死。

**定位手法**（推荐第一个）：

* `faulthandler.dump_traceback_later(45, exit=True)` —— 挂住 45 秒后打印**所有
  线程**的栈再退出。当时一眼看到主线程停在
  `_on_report_finished → QMessageBox`，而另一个线程还停在预加载的 `wait()` 上，
  区分"真卡死"和"只是慢"也靠它；
* 给 pytest 进程发 `SIGINT` 看当前栈：也能用，但被 Qt 事件循环吞掉的情况出现过，
  不如 faulthandler 稳；
* 排查期间先把输出**写进文件**（`> logs/xxx.log 2>&1`）再看，不要套 `tail`。

**规则**：

1. GUI 用例里调用任何"可能弹框"的主窗口方法前，先
   `patch.object(QMessageBox, "information", return_value=QMessageBox.StandardButton.Ok)`
   ；必要时连 `warning` / `critical` 一起 patch（`_close_window()` 辅助函数已经
   内建了这一层，直接用它关窗口最省事）；
2. 反过来：新写"会弹框"的功能时先想一句"测试会不会踩到"，并在用例里显式处理
   —— 能不用模态框就不用（状态栏提示 / 面板内提示优先）；
3. 一个用例里若分多段（如"关开关 / 开开关"两种配置），每段都要**自带** patch，
   别指望上一个 `with` 块还生效。

## 2. 被样式表定过颜色的控件，setEnabled(False) 不会自动变灰

**症状**：设置页把某行的下拉框置灰（`combo.setEnabled(False)`）后，下拉框自己变灰了，
但同一行的文字（`QLabel`）颜色一点没变；单独给 `QLabel` 调 `setEnabled(False)` 也一样，
`label.palette()` 里禁用态的 `WindowText` 仍是正常色。

**成因**：`ui/theme.py` 的全局样式表里有 `QWidget { color: <正常色> }`。Qt 样式表的
颜色规则在**所有状态**下都生效，会盖掉禁用态调色板；只有显式写了 `:disabled` 选择器的
规则才会在禁用时换成另一颜色。

**定位手法**：把同一段文字画两遍（一个 enabled、一个 disabled）后抓图取像素值，
颜色完全一致即可确认；再补一条 `QLabel#xxx:disabled { color: ... }` 重抓，
颜色变暗即验证规则生效。

**规则**：

1. 任何想靠 Qt 自动调色板"置灰"的控件，先看全局样式表有没有给它定 `color`；
   定了就必须自己补 `:disabled` 规则（本仓库：`QLabel#settingsRowLabel:disabled`）；
2. 判断某个控件到底灰没灰，用**抓图像素**或 `isEnabled()`，不要只看 `palette()`
   —— 样式表生效时调色板不是最终呈现的颜色；
3. 通用置灰样式统一放 `ui/theme.py`，不要在对话框里到处 `setStyleSheet`。

## 3. 样式表的 15px 与 QFont(family, 15) 的 15 不是一回事

**症状**：按标题字号估算侧边栏宽度时，量出「MangaProof 返修单」约 180px，于是预留
210px 宽；实际渲染后文字只有 135px，多出的一块空白把内容区挤窄了 30px。

**成因**：`QFont(family, 15)` 的第二个参数是**点**（磅值），15pt 在 96dpi 下约 20px；
而样式表里的 `font-size: 15px` 是**像素**。两者行高相差约 35%，按 pt 量出来的宽度 /
行高直接拿去排 px 尺寸必然偏大。

**定位手法**：把两种字体各画一行同一段文字，比较 `QFontMetrics.horizontalAdvance()` /
`height()`；或直接看 `widget.font().pixelSize()` 与 `pointSizeF()`，确认当前生效的是哪个单位。

**规则**：

1. 要与 QSS 字号对齐时，用 `QFont.setPixelSize()`（或从 `widget.font()` 拷贝后改），
   不要用 `QFont(family, size)` 构造；
2. 行高 / 宽度要参与布局计算时，宁可显式 `setSizeHint` / `setFixedHeight`，不要依赖
   "QSS 生效后的 `fontMetrics()`"——QSS 字号要等窗口显示后才进 `fontMetrics()`；
3. 量文字尺寸前先确认字体族已加载（MiSans 没加载时量到的是回退字体的宽度）。

## 4. 清空凭证只清明文、不删 keyring，等于"清了个寂寞"

**症状**：在更新页把 MirrorChyan CDK（或 GitHub Token）清空、点保存、关掉窗口再打开，
输入框里又出现了原来那串值。

**成因**：读取是 keyring 优先（`load_*` → `get_password` → 才看 settings.json），
而当时的 `save_cdk("")` 只把空串写进 settings.json，**没有删除 keyring 条目** ——
于是下次打开照旧从 keyring 把旧值读回来。表面上"保存成功"，实际什么都没清掉。

**定位手法**：连着打开两次更新页，对比 `keyring.get_password("MangaProof", "mirrorchyan_cdk")`
与 settings.json 里的 `update.mirrorchyan_cdk`；两者不一致即可确认是"只清了一处"。
注意 keyring 能不能用要用 `keyring_available()`（真实 set/get/delete 探测），
不能只看 import 是否成功。

**规则**：

1. 凭证的"清空"是**删除语义**：keyring 条目与配置文件明文一起删
   （`mangaproof/update/cdk_store.py::_save_secret` 空值分支），删完再回读一次确认；
2. keyring 能读不能写时（少见但真实：无桌面会话），既要写明文，也要把旧条目删掉，
   否则 `load_*` 会继续读到旧值，表现为"保存了但没生效"；
3. 交给后台线程的凭证一律**读控件文本**，不要读 `draft` —— 写 keyring 成功后
   `draft` 里那个字段会被清空（`save_*` 的既有约定），读 `draft` 只会拿到空串；
4. 界面上"改凭证"与"保存"是两件事：改动不置灰、不让已查到的结果失效，
   点「保存并检查更新」/「下载更新」时才落盘（与 CDK 的语义保持一致）。
