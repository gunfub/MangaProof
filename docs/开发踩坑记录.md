## 1. 未 patch 的模态对话框会把 offscreen GUI 测试永久卡死

**症状**：pytest 跑到某个 GUI 用例就没有任何输出、也不报错，一直挂着不结束；
用 `| tail` 之类管道时更惨 —— 连"卡在哪个用例"都看不到（管道缓冲会把日志全
藏起来，直到进程退出）。

**真实案例**（2026-10-08，返修单选项窗口那次改动）：
`tests/test_gui_smoke.py::test_report_options_switch_controls_dialog` 第 ① 段
直接调 `window.generate_report_dialog()` 出报告，只 patch 了
`ReportDialog.exec`，**漏了 `QMessageBox.information`**。报告生成完成后
`MainWindow._on_report_finished()` 会弹「已生成：<路径>」信息框
（`mangaproof/ui/main_window.py`），而测试这边正卡在 `_wait_for_report()` 的
`app.processEvents()` 里等后台线程收尾 —— 事件循环一进模态框就再也出不来。

**成因**：`QMessageBox.information / warning / critical` 是静态方法，内部自带
事件循环并阻塞调用方；`app.processEvents()` 推不动它，offscreen 平台又没有真人
去点「确定」，于是死等。注意这个坑是**成对**的：被测代码弹框（正常功能）+
测试没 patch（遗漏），两边都没错，合起来才卡死。

**定位手法**（推荐第一个）：

* `faulthandler.dump_traceback_later(45, exit=True)` —— 挂住 45 秒后打印**所有
  线程**的栈再退出。当时一眼看到主线程停在
  `_on_report_finished → QMessageBox`，而另一个线程还停在预加载的 `wait()` 上，
  区分"真卡死"和"只是慢"也靠它；
* 给 pytest 进程发 `SIGINT` 看当前栈：也能用，但被 Qt 事件循环吞掉的情况出现过，
  不如 faulthandler 稳；
* 排查期间先把输出**写进文件**（`> logs/xxx.log 2>&1`）再看，不要套 `tail`。

**规则**：

1. GUI 用例里调用任何"可能弹框"的主窗口方法前，先
   `patch.object(QMessageBox, "information", return_value=QMessageBox.StandardButton.Ok)`
   ；必要时连 `warning` / `critical` 一起 patch（`_close_window()` 辅助函数已经
   内建了这一层，直接用它关窗口最省事）；
2. 反过来：新写"会弹框"的功能时先想一句"测试会不会踩到"，并在用例里显式处理
   —— 能不用模态框就不用（状态栏提示 / 面板内提示优先）；
3. 一个用例里若分多段（如"关开关 / 开开关"两种配置），每段都要**自带** patch，
   别指望上一个 `with` 块还生效。
