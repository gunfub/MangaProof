# MangaProof 位置解析快速路径 · 技术设计

> 目标：给「图层自动定位 + 自动缩放」加一条**零像素解析**的快速路径，
> 默认不改变桌面端行为；Android 默认走快速路径。
> 涉及代码：`camera/centering.py`、`config/settings.py`、`ui/viewer_widget.py`、
> `ui/main_window.py`、`ui/settings_dialog.py`；**`ui/preloader.py` 零改动**。
> 回归：`tests/test_position_mode.py`（新增）。

---

## 0. 结论摘要

1. 定位 / 缩放 / 蓝色虚线框 / 自动框选**统一走一个入口** `position_bounds()`，
   只有"目标矩形从哪来"分两条路：视觉内容包围盒（解像素）或 PSD 图层原始框（纯元数据）。
2. 快速模式**只短路"图层级"的像素工作**：图层预热不再进行、切图层永远同步、
   阶段 B 队列只剩背景图。**merged 与 bg 的预加载一行没动**——那是 Original 显示与
   闪切对比的必需品，与定位无关。
3. 快速模式是"纯元数据路径"：以后任何"让某些图层居中更准"的改进都只能加在
   visual 分支（代码注释 + 绊线测试 + 本文档共同守住这条线）。

## 1. 现状：定位这条链路长什么样

| 环节 | 位置 | 事实 |
|---|---|---|
| 图层结构 | `psd/document.py::build_layers` | `node.bbox` 直接存进 `LayerInfo.bounds`，**建列表时零成本** |
| 视觉边界 | `psd/layer_model.py::LayerInfo.visual_bounds` | 平坦层走 alpha 直取（uint8 掩码），其余走 `composite/topil`（整层 RGBA）；结果只缓存 4 个 int，**过程要一份图层像素** |
| 居中 + 缩放 | `camera/centering.py` + `ui/viewer_widget.py::recenter_on_layer` | 目标矩形 → 矩形中心进相机、`fit_zoom()` 算缩放 |
| 蓝色虚线框 | `ui/main_window.py::_refresh_viewer_outline` | 视觉边界；无内容不画 |
| 自动框选 | `camera/centering.py::auto_box_rect` | 视觉边界（无则回退 bbox）±5px |
| 预热 | `ui/preloader.py` | 邻域 6 页 × 每页每个图层都算视觉边界；结果贴 `has_visual_bounds()` |
| 快路径门闩 | `main_window.py::_target_layer_warm / _request_layer_switch` | 只有预热过才同步切图层，否则后台线程 + 进度框 |

**成本实测**（本机，2451×3460 页；样本 6–15 层/页）：

| 指标 | 实测 |
|---|---|
| 预热一页（真实分析路径） | 32–89 ms，LRU +0.8–2.0 MB，瞬时 RSS +8–18 MB |
| 单个"非平坦"大图层（蒙版/特效/剪贴） | 约 0.3 s，最大约 1 s（整层 RGBA 解码） |
| 首次切到某图层的视觉边界计算 | 2.9–13.7 ms（样本）；非平坦大图层同上 |
| 快速模式的定位算术 | 0.002–0.005 ms/次（1000 次 0.26 ms） |
| 一页图像缓存（merged/bg 各 numpy+QImage） | 4 × 32.4 MB ≈ 130 MB —— **与定位无关，本次不动** |

> 样本里预热便宜，是因为大像素层恰好是"平坦层"（走 alpha 直取、不进 LRU）。
> 真实工程里非平坦图层越多、越大，预热的 CPU 与内存代价按层数线性增长。

## 2. 目标与非目标

**目标**

- 新增"快速"定位依据：直接取 PSD 图层自带的 `x / y / w / h`，零像素解析；
- 快速模式下：切图层不进入异步等待、不弹进度框、不排图层预热；
- 蓝框与自动框选与定位**同源**（同一个矩形），语义自洽；
- 桌面默认行为与改动前**逐项一致**（现有测试一行不改仍全绿）。

**非目标（明确不做）**

- 不改 merged / bg 的解码与预加载，不改 QImage 预热池，不改预加载窗口与内存策略；
- 不在快速模式里做任何"补偿精度"的处理（透明留白、蒙版、特效一律不修正）；
- 不追求"快速模式与视觉模式结果一致"——二者本就是精度 vs 速度的取舍。

## 3. 方案

### 3.1 单一入口

```python
POSITION_VISUAL = "visual"    # 视觉内容包围盒（解像素，精准）
POSITION_FAST   = "fast"      # PSD 图层原始框（零解析，快）

def position_bounds(info, position_mode=POSITION_VISUAL, alpha_threshold=0.0) -> LTRB | None
def position_center(info, position_mode=..., alpha_threshold=0.0) -> (x, y) | None
def auto_box_rect(info, margin=5.0, alpha_threshold=0.0, position_mode=POSITION_VISUAL)
```

| 模式 | 返回 |
|---|---|
| `visual` | 视觉边界；完全透明时按需求 §18.1 回退 `info.bounds`（**与改造前一致**）；都不可用 → `None` |
| `fast` | `info.bounds`；`right<=left` 或 `bottom<=top` → `None` |

`None` 一律表示"没有可用的定位矩形"：相机保持不动（不会把视图拖到 `(0,0)`）。

### 3.2 接线

| 位置 | 视觉模式 | 快速模式 |
|---|---|---|
| `ViewerWidget.recenter_on_layer` | 视觉边界居中 + 缩放 | 原始框居中 + 缩放（同一套相机/缩放公式） |
| `_refresh_viewer_outline` | 视觉边界 | 原始框（与本次居中矩形同源） |
| `auto_box_current_layer` | 视觉边界 ±5px | 原始框 ±5px |
| `_target_layer_warm` / `_request_layer_switch` | 未预热 → 后台 + 进度框 | 恒就绪 → 同步切换 |
| `_schedule_preloads` 的阶段 B | `WARM_ALL`（背景图 + 全部图层） | `""`（只补背景图） |
| `_update_preload_label` | "图层预热完成 / 预热中…" | "背景图就绪（快速定位：图层不预热）" |

### 3.3 为什么 `preloader.py` 一行都不用改

`PreloadWorker._process()` 的 `KIND_EXTRA` 分支：

```python
doc.prepare_bg()                       # 背景图：两种模式都照常
if layer_id == WARM_ALL: self._warm_all_layers(doc)
else:                    self._warm_layer(doc, layer_id)   # layer_id 为空 → 立即 return
```

快速模式下主窗口把任务里的 `layer_id` 从 `WARM_ALL` 换成 `""`，
`_warm_layer("")` 本来就早退 —— 于是"跳过图层预热、保留背景图预取"
**只靠任务内容表达**，预加载线程不需要知道"定位模式"，也就不会把两种关注点
纠缠在一起。

### 3.4 避免"空转排队"

阶段 B 的入队判据不能再写成 `not doc.has_bg() or not all_layers_warm(doc)`
——快速模式下视觉边界永远不算，`_all_layers_warm()` 恒为 `False`，每次切页都会
把 6 个页面重新排队（空转任务 + 状态栏闪烁 + 真正要的背景图排到后面）。
统一收敛到 `_extra_warm_spec(doc)`：

| 条件 | 任务 |
|---|---|
| 视觉模式且图层未预热 | `WARM_ALL` |
| 否则背景图未准备 | `""`（只补背景图） |
| 都齐了 | `None`（不入队） |

### 3.5 平台默认

- 桌面（Windows / Linux / macOS）：`POSITION_VISUAL`，精度优先；
- Android：`POSITION_FAST`，速度与内存优先（`default_position_mode()` 用
  `utils/platform.is_android_strict()` 判定，不看环境变量）；
- `settings.json` 里显式写过 `"position_mode"` 的**一律尊重**（Android 上也不覆盖）；
  只有缺键 / 非法值才落平台默认；
- 设置页「恢复默认」同样回到平台默认，保证"显示的档位 = 生效的档位"。

### 3.6 设置项

分类页「缩放与标注显示」，紧跟「图层自动显示比例」：

```
图层定位依据：  [ 视觉内容边界（精准，逐层解析像素） ▾ ]
                [ PSD 图层原始框（快速，零像素解析）  ]
```

用下拉而不是开关：这是两档取舍，不是布尔开关；与「对比模式 / 问题红框显示」同类。
切换后即时生效（重新定位 + 刷新蓝框 + 重排预加载队列），状态栏与「定位当前图层」
按钮 tooltip 都会标出当前依据。

## 4. 边界与行为细节

| 情况 | 行为 |
|---|---|
| bbox 退化（空图层） | 保持相机；蓝框/自动框选返回 None，状态栏提示 |
| 透明留白 / 蒙版 / 特效 / 非 100% 变换 | 快速模式按原始框居中，可能偏、可能比内容小 —— 刻意的取舍，不补偿 |
| 图层组 | 不进可监制列表，不受影响 |
| 同时开启「bg 独立比例」 | bg 判定仍可能解析像素（**既有逻辑**，与本模式无关）；想最省就关掉该项 |
| 快速 → 视觉（热切换） | 当前层未预热时走带进度框的异步预热路径，避免 UI 线程冻结；其余页照常排队预热 |
| 视觉 → 快速（热切换） | 立即重定位；预热队列改回"只补背景图"；已算过的视觉边界保留不动 |
| 关闭「蓝色虚线边界框」 | 只影响绘制，不影响定位 |

---

## 5. 不变量（改动前必读）

1. **快速分支禁止任何像素提取 / 缓存**：`load_image`、`load_bounds_image`、
   `visual_bounds`、alpha 直取、composite —— 一个都不许调；
2. 精度改进（蒙版、特效、透明留白、智能对象变换……）**只做在 visual 分支**；
3. 默认模式（桌面）行为必须与改动前一致：视觉边界 → 无内容回退 Bounds → 都无效保持相机；
4. merged / bg 的解码与预加载不因定位模式改变。

守住方式：`tests/test_position_mode.py` 用"绊线图层"（任何像素接口被调用即抛
AssertionError）覆盖定位、蓝框、自动框选、切图层四条路径；另有一条端到端用例
断言"快速模式打开任务后没有任何图层被算过视觉边界"。

## 6. 测试

`tests/test_position_mode.py`：

- 纯函数：两种模式的矩形来源、世界坐标偏移、透明回退、退化矩形、自动框选跟随模式；
- 零像素：绊线图层在快速模式下全链路可用；
- Viewer：相机中心 = 原始框中心、zoom = `fit_zoom(原始框)`、退化矩形不动相机；
- 主窗口：蓝框 = 原始框、切图层同步且不排预热/不弹进度框、阶段 B 只补背景图且
  不重复排队、切回视觉模式走异步预热、按钮 tooltip 反映当前依据；
- 设置：桌面/Android 平台默认、缺键与非法值回落、显式值优先、保存往返、
  设置页下拉映射与「恢复默认」。

全量回归：`QT_QPA_PLATFORM=offscreen uv run python -m pytest tests/ -q`。

## 7. 已知边界（本次不做，留档）

一页 2451×3460 的图像缓存约 **130 MB**（merged numpy + merged QImage + bg numpy +
bg QImage，各 32.4 MB），6 页预加载窗口合计约 780 MB —— 这是常驻内存的大头，
**与定位算法无关**，本次按要求不做任何改动。若将来要压这部分，可行的方向是
"邻域只留 numpy、QImage 只给当前页"（实测 QImage 转换仅 10–15 ms，却每页常驻
32.4 MB），属于独立议题，需单独立项与验证。
