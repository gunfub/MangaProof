# MangaProof 自更新系统需求规格

## 0. 更新目标

MangaProof 增加完整的跨平台自更新系统：

* Windows x64
* Linux x64 / arm64
* macOS x64 / arm64
* Android arm64 / x86_64

桌面端：

```text
MangaProof
    ↓
检查更新
    ↓
发现新版本
    ↓
用户点击“下载更新”
    ↓
下载完整更新包
    ↓
SHA-256 校验
    ↓
启动 MangaProof-update-installer
    ↓
主程序退出
    ↓
安装器备份数据 / 替换程序 / 恢复数据
    ↓
启动新版
    ↓
新版加载旧数据成功
    ↓
新版主动写入成功标记
    ↓
安装器确认更新成功
    ↓
清理旧版本与临时文件
```

Android：

```text
检查更新
    ↓
发现新版本
    ↓
用户点击“下载更新”
    ↓
下载 APK
    ↓
SHA-256 校验
    ↓
写入系统 Download
    ↓
调用系统安装器
```



GitHub Release Tag 同样采用该格式。

# 3. 版本判断

MirrorChyan 返回：

```json
{
    "version_name": "v1.0.0",
    "version_number": 2
}
```

其中：

```text
version_name
```

为软件版本。

```text
version_number
```

为 MirrorChyan 服务端资源上传计数。

更新判断只能使用：

```text
目标版本 > 当前版本
```

`version_number` 不得参与版本判断。

---

# 4. 分支语义

用户选择分支只是指定：

> “以后从这个分支检查新版本。”

不是分支切换工具。

只要目标版本高于当前版本，就允许升级。

例如：

```text
当前：v1.0.0
beta：v1.1.0.beta
```

允许更新。

例如：

```text
当前：v1.0.0.beta
stable：v0.9.0
```

不允许更新。

# 6. 平台专用模块

平台特有逻辑不得全部在启动阶段导入。

采用运行时判断：

```text
判断系统
    ↓
只导入对应平台模块
```

例如：

```text
mangaproof/update/platform/
├── windows.py
├── linux.py
├── macos.py
└── android.py
```

平台专用第三方库也在平台模块内部延迟导入。

目标：

* Windows 不加载 Linux/macOS 专用依赖
* Linux 不加载 Windows 专用依赖
* Android 不加载桌面提权依赖
* 减少启动负担
* 减少跨平台构建问题

---

# 7. PyInstaller 依赖声明

由于平台模块采用动态导入，PyInstaller 可能无法通过静态分析发现专用依赖。

因此：

```text
packaging/main_win.spec
packaging/main_linux.spec
packaging/main_macos.spec
```

分别显式声明对应平台的：

* hidden imports
* binaries
* datas

不得为了静态分析而将所有平台依赖全部塞进所有平台的构建产物。


发现更新后：

```text
[ 保存并检查更新 ] [ 下载更新 ] [ 清理升级缓存 ]        [ 取消 ]
                     ↑ 由置灰变为可用
```

下载完成并通过校验后，中间同一位置显示：

```text
[ 保存并检查更新 ] [ 安装更新 ] [ 清理升级缓存 ]        [ 取消 ]
```

三个动作按钮**紧挨着排在最左**（同属更新流程），「取消」单独留在最右。

**2026-09-24 修订**（左侧按钮语义固定、右侧按钮常驻）：

* 左侧按钮语义**固定**为“保存配置 + 检查更新”，文案永不改变；右侧按钮常驻占位
  （未检查出更新时置灰），按状态承担“下载 / 安装”两个后续动作。
* 旧版把三个动作挤在同一个按钮上（检查更新 → 立即更新 → 立即安装并重启），
  而“保存配置”只挂在第一支上：检查完之后再改代理/限速，点下一步时既不生效也不
  落盘，改分支/渠道更是被静默忽略。改版后**下载前也会保存**（见 §13）。
* 分支或渠道在检查之后被改动 → 右侧按钮置灰并提示重新检查：更新包是按检查时的
  分支与渠道定位的，不能让用户以为在下另一个分支的包。
* MirrorChyan 渠道在 CDK 为空时点「下载更新」→ 直接提示需要 CDK 或改用
  R2 / GitHub，不发请求（见 §11.8）。
* 「取消」语义不变（见 §13）。
* 「清理升级缓存」是第三个动作按钮（2026-09-24 追加）：清空升级用的两个临时目录
  并重建，清完同样必须重新检查更新（见 §82）。

# 24. R2 SHA-256 Manifest

R2 不使用固定名称：

```text
sha256.json
```

而是根据版本动态生成：

```text
MangaProof-<version>-sha256.json
```

例如：

```text
MangaProof-1.0.0-sha256.json
```

最终地址：

```text
stable/MangaProof-1.0.0-sha256.json
```

该文件名不得硬编码。

---

# 25. R2 Manifest 生成方式

R2 workflow 不重新计算发布包 SHA-256。

而是：

```text
GitHub Release API
        ↓
获取对应 Release
        ↓
获取全部 Release Assets
        ↓
读取每个 Asset 的 digest
        ↓
提取 sha256
        ↓
生成 MangaProof-<version>-sha256.json
        ↓
上传 R2
```

GitHub Release / Asset API 当前提供 Release 与 Asset 信息，并在 Asset 对象中提供 `digest`。


* 与主程序用的是**同一份**字体（调研报告 §11.2：「字体优先 MiSans，随包 `font/` 分发」）；
* 只做**进程内注册**：Windows `AddFontResourceExW(FR_PRIVATE)`、
  Linux `FcConfigAppFontAddFile(FcConfigGetCurrent(), …)`、
  macOS `CTFontManagerRegisterFontsForURL(…, Process)` —— **不写系统字体目录、
  不写 `~/.fonts`、不碰 fontconfig 缓存**（安装器是一次性程序，退出即消失）；
* 家族名按平台不同，两个都要认：GDI 用 nameID1（`MiSans Medium`）、
  CoreText / fontconfig 用 nameID16（`MiSans`）；
* 注册失败或文件缺失 → 自动回退系统字体链，不影响更新；
* 只带 Medium 一份：Windows / macOS 由系统合成粗体，Linux 的 Xft 不合成粗体
  → 标题 / 阶段 / 结果三个粗体标签退化为 Medium（已知并接受）。

# 59. 成功标记判断

安装器：

```text
启动新版
↓
等待 success marker
```

最多：

```text
60 秒
```

收到成功标记：

> 立即判定成功。

不继续等待剩余时间。

跟踪目标（2026-09-24 修订）：安装器跟踪的是**主程序进程本身**，不是"启动它用的
那个 pid"。macOS 用 `open -n -a` 拉起 .app 时 `open` 会立刻退出、app 是另一个
pid，因此 pid 消失后要按进程名找回主程序、换成它的 pid 继续等待（见 §60）。

---

# 60. 新版提前退出

如果**按进程名找不到主程序进程**，并且：

```text
success marker
```

还没有出现：

> 判定更新失败并进入 rollback。

不需要继续等待剩余 60 秒。

2026-09-24 修订（macOS 真机实测的误报失败）：

* 判据是"**主程序进程不存在**"，不是"安装器跟踪的 pid 消失了"：macOS 用
  `open -n -a` 启动 .app 时那个 pid 属于 `open`，它把启动交给 LaunchServices
  后必然秒退 —— 按 pid 判会**每次更新都误报失败**，而且回滚还会删掉正在启动的
  新版目录；
* pid 消失后先**按进程名查找主程序**：找到 → 换成它的 pid 继续等待成功标记
  （不算失败）；
* 找不到 → 给 **20 秒宽限期**（app 从 launchd 拉起、冷启动与 Gatekeeper 校验
  都要时间），宽限期结束仍然找不到才判失败；
* 查不了进程（`ps` 不可用）→ 当作"可能还活着"，等满 §59 的 60 秒再按超时处理，
  绝不因为查不到而提前判失败；
* 等待期间**不结束主程序**；只有等满 §59 的 60 秒超时才结束它并按 §62 回滚。

# 82. 清理升级缓存

按钮：

```text
清理升级缓存
```

点击后先弹窗确认（默认按钮为「取消」），确认后清空以下两个目录：

```text
TEMP/CACHE/MangaProof-update-package
TEMP/CACHE/MangaProof-update-installer
```

* Windows 用 `TEMP` / `TMP`，Linux / macOS 用 `XDG_CACHE_HOME` 或 `~/.cache`
  （同 §36/§37，路径由 `mangaproof/update/platform_dirs.py` 唯一提供）；
* 第一个目录里的**数据备份子目录（`MangaProof-update-data`）一并删除** ——
  它只是升级途中的临时中转副本（§49 复制出来、§56 恢复回去），不是持久化备份；
* 删除后**把两个目录重建为空目录**；
* **防护**：只认这两个固定目录名且必须正好位于更新临时根目录之下；名字或位置不符
  → 拒绝删除；目录不存在 → 跳过删除（不算失败）；软链接 → 跳过，绝不跟随；
  删除失败（占用/权限）→ 如实报告，且不影响另一个目录；
* 存在正在进行的检查或下载时按钮置灰；清理本身走后台线程，界面保持响应。

清理之后：**本轮检查结果作废**，需要重新点击「保存并检查更新」才能继续下载或安装。

弹窗文案必须说明：将清空哪两个目录；更新成功后桌面端会自动删除已下载的更新包；
更新安装器在 Windows 上无法自行删除、会在下一次更新时被覆盖，在 Linux / macOS 上
会自行删除 —— 因此这两个目录通常只残留少量日志；只有在升级失败时，手动清理才是
一个好选择。

**本功能完全实现在主程序侧**（`mangaproof/update/cache.py` + 更新页按钮），
不写进安装器。

# 83. 安装器防误启动

安装器是**内部程序**：只应由主程序的「更新」功能启动。直接双击 / 手工运行时必须
给出可见提示并优雅退出 —— **不允许"静默退出"**（2026-09-25 实测：windowed 构建下
缺参启动只写一行日志、退出码 2，用户界面上什么都没有，看起来像程序坏了）。

判定与行为：

| 情况 | 行为 | 退出码 |
| --- | --- | --- |
| 缺参 / 参数非法（argparse 失败） | 弹深色提示窗 → 用户确认后退出 | 2 |
| 没有 `--parent-pid` **且**检测到主程序正在运行 | 拒绝执行并说明原因 | 10 |
| 给了 `--allow-direct-launch`（调试，§45） | 跳过上面两条检查，日志留痕 | — |
| 源码运行（非 PyInstaller 打包） | 不弹提示框，保持命令行报错 | 2 |
| `--cli` / 无图形会话 / tkinter 缺失 | 降级为 stderr + 日志，绝不阻塞 | 2 |

提示窗版式（**与安装器主窗口同一套视觉**，§11.2；一次只问"退出"这一件事）：

```text

此程序不能直接打开，只能由 MangaProof 主程序的            ← 正文：正文色 11
「更新」功能自动调用。

如需更新：打开 MangaProof →「关于」→「检查更新」→
「保存并检查更新」，按提示完成。                          ← 操作提示：次要文字色 10

缺少启动参数：--install-dir、--package                    ← 诊断行：警告色 9
（按实际缺失项生成，没有缺参时不显示这一行）

                                            [ 退出 ]      ← 主按钮在右下角
```

* 提示窗沿用 §11.2 的调色板（主背景 `#2b2d30`、正文 `#e4e6eb`、次要 `#a0a4ab`、
  警告 `#f5a623`、按钮 `#3a3d42`／悬停 `#45494f`／按下 `#2d5f8a`）与随包 MiSans，
  按钮在右下角；**Esc / 回车 / 关窗都等于点「退出」**；
* **降级链**：深色提示窗 → 系统原生 `messagebox`（深色窗建不起来时）→ stderr + 日志；
  任何一步失败都不许抛异常、不许卡住（宁可少一句提示，也不能让安装器挂在提示上）；
* 全过程**不触碰安装目录、不写状态文件、不写成功标记**；提示只做提示，
  不"自动修复"、不"找不到主程序就自己装"；
* 直接启动的日志写进 `TEMP/CACHE/MangaProof-update-installer/`（该目录存在时用），
  这样 §82「清理升级缓存」能一起清掉；目录不存在则**不创建**，退回系统临时根目录；
* 「主程序正在运行」的判定复用 §46 的进程名口径（`MangaProof`）；`ps` 查不了时
  **只记日志、不拦截**（与 §46 的保守哲学一致）；
* 本版**不做**：安装器自检自己的运行目录（§40 仍由主程序负责把安装器复制到临时
  目录运行；安装器保持"从哪运行都能跑"，避免影响单测、开发与排障）、父进程名校验
  （提权后父进程是 `consent.exe` / `pkexec` / `osascript`，必然误判）、调用凭证签名。

# 84. 源码运行只检查、不下载

以源码方式运行（非 PyInstaller 打包产物）时，**允许检查更新，但不开放更新包下载**。

* 「保存并检查更新」照常可用，检查结果照常显示 —— 版本、更新说明、文件、大小一个不少；
* 右侧按钮**恒置灰**，文案仍是「下载更新」（沿用 §11.7 / §13 的"常驻置灰、不做
  show/hide、文案只在 `_sync_actions` 一处推导"）；tooltip 说明原因；
* 输出区写入提示，位置在**版本行之后、分支/文件/大小之前**（理由见下）；
* **没有更新时不提这句**，保持 §32 的「当前已经是最新版本」原文案；
* 即使绕过按钮直调下载入口，也**不发下载请求、不提交配置**（被拒绝的操作不产生
  副作用，与 §11.8 缺 CDK 的守卫同一个原则）；
* 源码运行下永远拿不到已下载的包，因此「安装更新」分支天然不可达 ——
  **不额外加安装守卫**。

提示文案：

```text
当前以源码方式运行，不提供更新包下载。

请在项目目录执行：
    git pull
以拉取最新源代码。
```

**位置不是随手放的**：输出区固定高度 180px（§31 的布局约束），且每个新动作都会把
滚动位置归零 —— 提示排在「文件 / 大小」后面就会掉出首屏，用户只看到一个灰掉的
「下载更新」却读不到原因。

**理由**：更新包是打包好的二进制发行版（Windows / macOS `.zip`、Linux `.tar.gz`、
Android `.apk`，见 `mangaproof/update/detector.py` 的 `_TARGETS`），对源码树没有意义；
源码运行的正确更新方式是 `git pull`。

判定：`mangaproof/utils/platform.py::is_source_run()`，判据只有 `sys.frozen` 一条，
与 `config/paths.py::get_app_dir()`、`console.py` 的控制台可见性判定同源；
运行形态**在更新页构造时定一次**，不由每次点击重算。

* **Android 不是"源码运行"**（2026-09-26 修订）：p4a 打的 APK 不设 `sys.frozen`，
  但它同样是打包发行版 —— 判定里必须把它排掉，否则安卓端会被禁用更新包下载、
  还提示"请 git pull"。落地细则见 §85；
* **本功能完全实现在主程序侧**（`mangaproof/ui/update_dialog.py` + 上述谓词），
  不写进安装器 —— 检查与下载本来就不归安装器负责（安装器只管 §41~§63 的替换流程）。

# 85. Android 安装更新交给系统安装器

§65 / §66 的落地细则（2026-09-26 需求方确认）。

```text
检查更新 → 下载更新 → 校验（下载时）→ 写系统 Download → 交给系统包管理器
```

Android **不使用**独立安装器（§65），因此桌面那条
"启动安装器 → 确认拉起 → 主程序退出 → 安装器替换文件 → 拉起新版"的链路在
Android 上整条不适用。

## 85.1 检查与下载：与桌面一致，只有落盘目录不同

* 检查走同一条链路（§17、§20 的无凭据请求 + Android 的 rid/user_agent，§18）；
* 下载走同一条链路（§33~§35），**唯一差别是落盘目录**：
  * 桌面（§36/§37）：`TEMP/MangaProof-update-package`、`CACHE/MangaProof-update-package`；
  * **Android**：**系统 Download**（`/storage/emulated/0/Download`，取值见
    `mangaproof/update/platform/android.py::download_dir()`）。
    需要用户已授予「所有文件访问」；未授予时在下载阶段如实报错，不静默失败。
* 包名沿用 §22 的资产命名（`MangaProof-<version>-android-<arch>.apk`）。

## 85.2 安装：调起系统安装器

* 用 `QDesktopServices.openUrl()` 打开已下载的 APK，由**系统包管理器**完成安装；
* **不退出主程序**：系统安装界面覆盖在本程序之上，安装时由系统结束本进程。
  `openUrl` 只能回报"是否成功发起"，拿不到安装结果，因此**不显示"安装成功"**，
  也不做 §57/§58 的成功标记握手（那套是给桌面安装器拉起新版用的）；
* 实现依据（**不引入 JNI / pyjnius**）：Qt 的 Android 平台层对 `file://` URL
  （SDK 24+）会自动用 `FileProvider` 换成可共享的 `content://` URI，并以
  `ACTION_VIEW` + `FLAG_GRANT_READ_URI_PERMISSION` 调起 Activity。
  这也符合 `storage/picker.py` 里"自建 Java 原生桥勿再引入"的既有决定；
* **构建期前提**：
  1. 清单声明 `androidx.core.content.FileProvider` —— Qt 是**在清单里枚举**该
     provider 来选 authority 的，而本项目的清单来自 p4a 模板（不含任何 provider），
     所以由 `packaging/android/p4a_hook.py` 注入；类名**必须**是
     `androidx.core.content.FileProvider` 本身（Qt 按类名子串匹配，自建子类会被忽略）；
  2. 可共享目录 `res/xml/qtprovider_paths.xml`，**只开放系统 Download**
     （不照抄 Qt 模板的 `path="/"`）；
  3. 权限 `android.permission.REQUEST_INSTALL_PACKAGES`（Android 8+ 必需）；
  4. **Gradle 依赖 `androidx.core:core`**（`android.gradle_dependencies`）。
     ⚠️ 这条不是"预防性"的：清单里声明了 provider，Android 会在**进程启动时**
     （`ActivityThread.installContentProviders`）就实例化它 —— 类不在包内就是
     `ClassNotFoundException`，**启动即崩**；而**构建期完全不报错**（清单合并器
     不校验 provider 类是否存在）。
     2026-10-06 实测：v1.1.14.alpha 的 APK 6 个 dex 里**没有任何 androidx 类**
     （Qt 与 p4a 都不带），所以必须显式加依赖。
     这条由 CI 的「Verify APK native libs and splash resources」两步卡死：
     清单里有 provider、dex 里有该类，缺任一即失败（见 `.github/workflows/android.yml`）。
     ⚠️ 校验二进制清单时**必须先去掉 NUL 字节**（`tr -d '\0'`）：AXML 的字符串池是
     **UTF-16LE**，直接 grep ASCII 永远匹配不到。2026-10-06 因此假失败过一次 ——
     APK 已经编好，却因为校验方法本身错而报"清单缺少 FileProvider"，把整个构建卡在最后一步。
     另注意两处判据写法不同：**清单里是点号**（`androidx.core.content.FileProvider`），
     **dex 里是斜杠**（类型描述符 `Landroidx/core/content/FileProvider;`）。
* **用户侧**：**若系统拦截安装**，需放行「安装未知应用」；调起失败时提示这一步，
  并给出在文件管理器中手动安装的退路。
  ⚠️ **不要把它写成"必须先授予"的断言**：2026-10-06 需求方实测，一台**未放行**
  「安装未知应用」而**已放行**「所有文件访问」的设备上，安装被成功调起；原因未定位
  （两者在 AOSP 里是独立 appop，查不到耦合机制），最可能是 ROM 安装流程实现差异。
  该现象**只作观察记录，不作为可依赖的行为**。
* APK 必须与已安装应用**同签名**（CI 已用仓库 keystore 重签；fork 构建的
  `-unsigned.apk` 装不上）。

## 85.3 完整性校验：安卓只做"下载时"这一层

需求方决策：**下载时校验即可** —— Android 由系统包管理器做**签名校验**，
主程序不必再叠加一层。

* 保留：下载时的渠道哈希（`plan.sha256`）+ 下载后本地重算并展示（§35）；
* **不适用**：桌面安装器的 4 步复核（`updater/verify.py`、`--sha256` 复核）——
  安卓没有那个安装器，也没有对应钩子。**不要**以为安卓还校验了那一步。

## 85.4 APK 不自动清理

需求方决策：**不清理**，交给系统与用户（APK 就在系统 Download 里，用户看得见、
可自行删除或重试安装）。因此不新增任何自动清理逻辑。

## 85.5 「清理升级缓存」在 Android 恒置灰

那两个目录（`MangaProof-update-package` / `MangaProof-update-installer`）是
**桌面安装器体系**的东西：Android 既没有独立安装器，更新包也已落到系统 Download
（不在那两个目录里）——清它无事可做，还会让人误以为能清掉已下载的 APK。
沿用既有约定：**只置灰、不改文案、不做 show/hide**。

# 86. 返修单生成：选项窗口由设置统一控制

「生成返修单」有两条触发路径，行为原本不一致：手动（工具栏 / `Ctrl+R`）会弹选项
窗口（名称 / 页面图像格式 / JPEG 质量 / 总览表隐藏无问题 PSD），全部图层检查完
之后的自动生成则按设置静默出报告 —— 参数只能在设置页里预先调，或者事后手动
重生成一次。

2026-10-08 需求方决策：**新增一个设置项，两条路径共用它**。

## 86.1 设置项

* 名称：**「生成返修单前显示选项窗口」**；
* `settings.json` 键：`report_show_options`，**默认开**；
* 位置：设置对话框「MangaProof 返修单」组内，紧接「完成监制后自动生成返修单」；
* 旧配置文件没有这个键 → 取默认值**开**（老用户不会静默失去弹窗）。

## 86.2 两条路径共用同一个开关

```text
开关开：手动 Ctrl+R → 选项窗口 ；  完成后自动生成 → 选项窗口
开关关：手动 Ctrl+R → 直接用设置 ；  完成后自动生成 → 直接用设置
```

* 关掉后**不失去任何配置能力**：名称 / 页面图像格式 / JPEG 质量 / 总览表选项在
  设置页里都有对应控件；
* 窗口里改过的格式 / 质量 / 总览选择照旧记回设置、下次沿用（**名称不记**，
  沿用现状）。

## 86.3 完成提示合并

会弹选项窗口时（自动生成开 **且** 选项窗口开），完成监制的告知由该窗口承担：
顶部绿字「✓ 所有图层已检查完成，将生成最终返修单」—— **不再先弹一次「监制完成」
提示框**，完成流程只打断一次。

不弹选项窗口时（关掉自动生成，或关掉选项窗口）提示框照旧 —— 否则"图层检查完了"
这件事就没有任何告知。

## 86.4 取消不自动重试

在选项窗口里点「取消」→ 本次不生成，且**不会自动重来**（本次完成已经提示过）；
需要时按 `Ctrl+R` 手动生成。`_completion_announced` 语义不变，不为此新增状态。

## 86.5 落地位置

* `mangaproof/config/settings.py`：字段 `report_show_options` + 读写（缺键回落默认开）；
* `mangaproof/ui/settings_dialog.py`：复选框与 tooltip（含"关掉选项窗口时以本页
  设置为准"的说明）；
* `mangaproof/ui/main_window.py`：`_generate_report()` 去掉 `interactive` 参数，
  弹不弹窗一律看设置；`_on_all_reviewed()` 按上方规则分流完成告知；
* `mangaproof/ui/dialogs.py`：`ReportDialog` 增加 `completed` 参数与顶部状态行。

# 87. 背景图层永不被隐藏过滤排除

背景：隐藏图层排除落地后，把「谁进可监制列表」和「谁当对比基准」绑成了
一件事 —— 建结构时只收可见层，选背景又只在列表里找，于是**被隐藏的 `bg` /
兜底层在选层之前就消失了**，基准落到"最底部可见层"上。实测原始工程文件
（`三角符号下的静谧日常.psd` 等 3 个同构文件）最底层的原版底图是隐藏的，基准
被选成了上层的修图底版。

2026-10-08 需求方决策：**背景层永不被排除**。

## 87.1 判据不变，只把候选集放回全集

* 背景层判据沿用 §24：名字**严格等于** `bg`（大小写敏感，`bg copy` / `BG` 不认）；
  没有 `bg` 名 → 取最底部、具有可用像素内容的图层；
* 判据的**候选集是全量图层**（含隐藏层、含藏在隐藏组/文件夹里的层）；
* 选中的背景层即使在 PSD 里是隐藏的，也照常进可监制列表，`LayerInfo.visible`
  如实记为 `False`（不再恒为 True）；
* 可见性只决定「谁进列表」，**不参与「谁当背景」的选择**；
* `bg 拷贝` **不豁免**：隐藏的 `bg 拷贝` 照旧不进列表（"独立自动显示比例"因此
  在它被隐藏时不生效，维持现状）。

## 87.2 性能约束

建结构发生在打开任务的**逐页扫描**里，而背景判定要读像素（§24 的"有可用像素
内容"）。因此豁免判断先走**零像素代价的结构快路径**——只有"隐藏层有可能是
背景"时才解析背景：

```text
存在隐藏层，且（有隐藏层名字严格等于 bg，或迭代序里第一个有 bbox 的图层是隐藏的）
    → 解析背景（结果缓存）；否则隐藏层不可能成为背景，直接跳过
```

普通文件（隐藏层都压在基准之上）建结构阶段**零额外像素提取**；无条件解析会让
每页多解一次全页像素（实测 11～250 ms/页），大文件夹的打开时间成倍上涨。

## 87.3 落地位置

`mangaproof/psd/document.py`：`build_layers()`（先收全量清单，选出背景后才做
可见性过滤）、`_hidden_bg_exemption()`（结构快路径 + 豁免集合）、
`_select_bg_layer()`（候选集改为全量图层）、`LayerInfo.visible` 语义。

# 88. 0 图层文件：文件栏直接算通过 + 图层区说明

背景：把图片拖进 Photoshop、未做任何处理直接保存的 PSD，文件里**没有任何图层
记录**（layer count = 0，只有 merged image）。样本 `local_samples/_001.psd`
实测即此结构：layer&mask 段 32 字节、layer info 段长 0、layer count 0，merged
完整可解。这种文件此前在界面上的表现是「图层区一片空白 + 文件栏 ○ 未监制」，
看不出是坏文件还是没内容。

2026-10-08 需求方决策：给 0 图层文件一个明确口径。

## 88.1 判定与显示

* **判定**：解析成功、但 PSD 里一个图层都没有 → 0 图层文件。必须与**解析失败**
  区分开（读不出来的文件不算通过）；
* **左侧文件栏**：对应文件直接显示 ✓ 通过；
* **右侧图层区**：显示说明文字（该 PSD 不含任何图层 / 常见成因 / 已标记为通过）；
* 只是**显示口径**，不写任何图层状态，任务文件不受影响；0 图层文件也不占进度
  （总计图层数为 0）。

## 88.2 未打开项目时不受影响

说明文字只在**确实打开这种文件**时出现；关闭任务 / 打开普通文件即清空，未打开
项目时两栏仍是初始空态。

## 88.3 图层区布局约束（实机反馈修正）

说明文字上线的第一版把图层列表一起隐藏了，产生两个实机可见的问题：**图层栏被
撑宽**（面板宽度反过来由这段文字决定）、**加粗的「图层」二字掉到中间**（多余
竖向高度摊到标题上，标题从 17px 被拉到 132～145px，文字在其中垂直居中）。约定：

* 标题竖向政策 `Fixed`：只占自己那一行的高度；
* 说明区横向政策 `Ignored` + 最小宽度 1：只按可用宽度折行，不参与决定面板宽度；
* 说明外套一层无边框滚动区：字号放得很大而图层栏很矮时，宁可滚动也不截断；
* 说明显示时**不隐藏列表**，改为把列表高度上限收成 0：宽度提示仍在，面板宽度
  与平时一致（首次布局也不会缩窄）；关闭说明时恢复高度上限。

`mangaproof/ui/main_window.py`：`_is_zero_layer_file()`、文件栏状态分流、
打开文件时给图层区传说明文字；`mangaproof/ui/layer_panel.py`：
`ZERO_LAYER_PLACEHOLDER` 与空态说明控件及其布局约束。
