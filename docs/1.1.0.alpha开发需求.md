# MangaProof 自更新系统需求规格

## 0. 更新目标

MangaProof 增加完整的跨平台自更新系统：

* Windows x64
* Linux x64 / arm64
* macOS x64 / arm64
* Android arm64 / x86_64

桌面端：

```text
MangaProof
    ↓
检查更新
    ↓
发现新版本
    ↓
用户点击“下载更新”
    ↓
下载完整更新包
    ↓
SHA-256 校验
    ↓
启动 MangaProof-update-installer
    ↓
主程序退出
    ↓
安装器备份数据 / 替换程序 / 恢复数据
    ↓
启动新版
    ↓
新版加载旧数据成功
    ↓
新版主动写入成功标记
    ↓
安装器确认更新成功
    ↓
清理旧版本与临时文件
```

Android：

```text
检查更新
    ↓
发现新版本
    ↓
用户点击“下载更新”
    ↓
下载 APK
    ↓
SHA-256 校验
    ↓
写入系统 Download
    ↓
调用系统安装器
```

* 断点续传

* 降级更新

# 2. 更新分支

支持：

```text
alpha

```

```text
alpha  → v1.0.0.alpha
beta   → v1.0.0.beta
```

GitHub Release Tag 同样采用该格式。

---

# 3. 版本判断

MirrorChyan 返回：

```json
{
    "version_name": "v1.0.0",
    "version_number": 2
}
```

其中：

```text
version_name
```

为软件版本。

```text
version_number
```

为 MirrorChyan 服务端资源上传计数。

更新判断只能使用：

```text
目标版本 > 当前版本
```

`version_number` 不得参与版本判断。

---

# 4. 分支语义

用户选择分支只是指定：

> “以后从这个分支检查新版本。”

不是分支切换工具。

只要目标版本高于当前版本，就允许升级。

例如：

```text
当前：v1.0.0
beta：v1.1.0.beta
```

允许更新。

例如：

```text
当前：v1.0.0.beta
stable：v0.9.0
```

不允许更新。

# 6. 平台专用模块

平台特有逻辑不得全部在启动阶段导入。

采用运行时判断：

```text
判断系统
    ↓
只导入对应平台模块
```

例如：

```text
mangaproof/update/platform/
├── windows.py
├── linux.py
├── macos.py
└── android.py
```

平台专用第三方库也在平台模块内部延迟导入。

目标：

* Windows 不加载 Linux/macOS 专用依赖
* Linux 不加载 Windows 专用依赖
* Android 不加载桌面提权依赖
* 减少启动负担
* 减少跨平台构建问题

---

# 7. PyInstaller 依赖声明

由于平台模块采用动态导入，PyInstaller 可能无法通过静态分析发现专用依赖。

因此：

```text
packaging/main_win.spec
packaging/main_linux.spec
packaging/main_macos.spec
```

分别显式声明对应平台的：

* hidden imports
* binaries
* datas

不得为了静态分析而将所有平台依赖全部塞进所有平台的构建产物。

```text
[                           ]

[ 不限速 ▼ ]

[ 保存并检查更新 ] [ 下载更新 ] [ 清理升级缓存 ]        [ 取消 ]
```

发现更新后：

```text
[ 保存并检查更新 ] [ 下载更新 ] [ 清理升级缓存 ]        [ 取消 ]
                     ↑ 由置灰变为可用
```

下载完成并通过校验后，中间同一位置显示：

```text
[ 保存并检查更新 ] [ 安装更新 ] [ 清理升级缓存 ]        [ 取消 ]
```

三个动作按钮**紧挨着排在最左**（同属更新流程），「取消」单独留在最右。

**2026-09-24 修订**（左侧按钮语义固定、右侧按钮常驻）：

* 左侧按钮语义**固定**为“保存配置 + 检查更新”，文案永不改变；右侧按钮常驻占位
  （未检查出更新时置灰），按状态承担“下载 / 安装”两个后续动作。
* 旧版把三个动作挤在同一个按钮上（检查更新 → 立即更新 → 立即安装并重启），
  而“保存配置”只挂在第一支上：检查完之后再改代理/限速，点下一步时既不生效也不
  落盘，改分支/渠道更是被静默忽略。改版后**下载前也会保存**（见 §13）。
* 分支或渠道在检查之后被改动 → 右侧按钮置灰并提示重新检查：更新包是按检查时的
  分支与渠道定位的，不能让用户以为在下另一个分支的包。
* MirrorChyan 渠道在 CDK 为空时点「下载更新」→ 直接提示需要 CDK 或改用
  R2 / GitHub，不发请求（见 §11.8）。
* 「取消」语义不变（见 §13）。
* 「清理升级缓存」是第三个动作按钮（2026-09-24 追加）：清空升级用的两个临时目录
  并重建，清完同样必须重新检查更新（见 §82）。

# 24. R2 SHA-256 Manifest

R2 不使用固定名称：

```text
sha256.json
```

而是根据版本动态生成：

```text
MangaProof-<version>-sha256.json
```

例如：

```text
MangaProof-1.0.0-sha256.json
```

最终地址：

```text
stable/MangaProof-1.0.0-sha256.json
```

该文件名不得硬编码。

---

# 25. R2 Manifest 生成方式

R2 workflow 不重新计算发布包 SHA-256。

而是：

```text
GitHub Release API
        ↓
获取对应 Release
        ↓
获取全部 Release Assets
        ↓
读取每个 Asset 的 digest
        ↓
提取 sha256
        ↓
生成 MangaProof-<version>-sha256.json
        ↓
上传 R2
```

GitHub Release / Asset API 当前提供 Release 与 Asset 信息，并在 Asset 对象中提供 `digest`。


* 与主程序用的是**同一份**字体（调研报告 §11.2：「字体优先 MiSans，随包 `font/` 分发」）；
* 只做**进程内注册**：Windows `AddFontResourceExW(FR_PRIVATE)`、
  Linux `FcConfigAppFontAddFile(FcConfigGetCurrent(), …)`、
  macOS `CTFontManagerRegisterFontsForURL(…, Process)` —— **不写系统字体目录、
  不写 `~/.fonts`、不碰 fontconfig 缓存**（安装器是一次性程序，退出即消失）；
* 家族名按平台不同，两个都要认：GDI 用 nameID1（`MiSans Medium`）、
  CoreText / fontconfig 用 nameID16（`MiSans`）；
* 注册失败或文件缺失 → 自动回退系统字体链，不影响更新；
* 只带 Medium 一份：Windows / macOS 由系统合成粗体，Linux 的 Xft 不合成粗体
  → 标题 / 阶段 / 结果三个粗体标签退化为 Medium（已知并接受）。

# 59. 成功标记判断

安装器：

```text
启动新版
↓
等待 success marker
```

最多：

```text
60 秒
```

收到成功标记：

> 立即判定成功。

不继续等待剩余时间。

跟踪目标（2026-09-24 修订）：安装器跟踪的是**主程序进程本身**，不是"启动它用的
那个 pid"。macOS 用 `open -n -a` 拉起 .app 时 `open` 会立刻退出、app 是另一个
pid，因此 pid 消失后要按进程名找回主程序、换成它的 pid 继续等待（见 §60）。

---

# 60. 新版提前退出

如果**按进程名找不到主程序进程**，并且：

```text
success marker
```

还没有出现：

> 判定更新失败并进入 rollback。

不需要继续等待剩余 60 秒。

2026-09-24 修订（macOS 真机实测的误报失败）：

* 判据是"**主程序进程不存在**"，不是"安装器跟踪的 pid 消失了"：macOS 用
  `open -n -a` 启动 .app 时那个 pid 属于 `open`，它把启动交给 LaunchServices
  后必然秒退 —— 按 pid 判会**每次更新都误报失败**，而且回滚还会删掉正在启动的
  新版目录；
* pid 消失后先**按进程名查找主程序**：找到 → 换成它的 pid 继续等待成功标记
  （不算失败）；
* 找不到 → 给 **20 秒宽限期**（app 从 launchd 拉起、冷启动与 Gatekeeper 校验
  都要时间），宽限期结束仍然找不到才判失败；
* 查不了进程（`ps` 不可用）→ 当作"可能还活着"，等满 §59 的 60 秒再按超时处理，
  绝不因为查不到而提前判失败；
* 等待期间**不结束主程序**；只有等满 §59 的 60 秒超时才结束它并按 §62 回滚。

# 82. 清理升级缓存

按钮：

```text
清理升级缓存
```

点击后先弹窗确认（默认按钮为「取消」），确认后清空以下两个目录：

```text
TEMP/CACHE/MangaProof-update-package
TEMP/CACHE/MangaProof-update-installer
```

* Windows 用 `TEMP` / `TMP`，Linux / macOS 用 `XDG_CACHE_HOME` 或 `~/.cache`
  （同 §36/§37，路径由 `mangaproof/update/platform_dirs.py` 唯一提供）；
* 第一个目录里的**数据备份子目录（`MangaProof-update-data`）一并删除** ——
  它只是升级途中的临时中转副本（§49 复制出来、§56 恢复回去），不是持久化备份；
* 删除后**把两个目录重建为空目录**；
* **防护**：只认这两个固定目录名且必须正好位于更新临时根目录之下；名字或位置不符
  → 拒绝删除；目录不存在 → 跳过删除（不算失败）；软链接 → 跳过，绝不跟随；
  删除失败（占用/权限）→ 如实报告，且不影响另一个目录；
* 存在正在进行的检查或下载时按钮置灰；清理本身走后台线程，界面保持响应。

清理之后：**本轮检查结果作废**，需要重新点击「保存并检查更新」才能继续下载或安装。

弹窗文案必须说明：将清空哪两个目录；更新成功后桌面端会自动删除已下载的更新包；
更新安装器在 Windows 上无法自行删除、会在下一次更新时被覆盖，在 Linux / macOS 上
会自行删除 —— 因此这两个目录通常只残留少量日志；只有在升级失败时，手动清理才是
一个好选择。

**本功能完全实现在主程序侧**（`mangaproof/update/cache.py` + 更新页按钮），
不写进安装器。

# 83. 安装器防误启动

安装器是**内部程序**：只应由主程序的「更新」功能启动。直接双击 / 手工运行时必须
给出可见提示并优雅退出 —— **不允许"静默退出"**（2026-09-25 实测：windowed 构建下
缺参启动只写一行日志、退出码 2，用户界面上什么都没有，看起来像程序坏了）。

判定与行为：

| 情况 | 行为 | 退出码 |
| --- | --- | --- |
| 缺参 / 参数非法（argparse 失败） | 弹深色提示窗 → 用户确认后退出 | 2 |
| 没有 `--parent-pid` **且**检测到主程序正在运行 | 拒绝执行并说明原因 | 10 |
| 给了 `--allow-direct-launch`（调试，§45） | 跳过上面两条检查，日志留痕 | — |
| 源码运行（非 PyInstaller 打包） | 不弹提示框，保持命令行报错 | 2 |
| `--cli` / 无图形会话 / tkinter 缺失 | 降级为 stderr + 日志，绝不阻塞 | 2 |

提示窗版式（**与安装器主窗口同一套视觉**，§11.2；一次只问"退出"这一件事）：

```text
无法直接启动                                            ← 标题：正文色 14 粗

此程序不能直接打开，只能由 MangaProof 主程序的            ← 正文：正文色 11
「更新」功能自动调用。

如需更新：打开 MangaProof →「关于」→「检查更新」→
「保存并检查更新」，按提示完成。                          ← 操作提示：次要文字色 10

缺少启动参数：--install-dir、--package                    ← 诊断行：警告色 9
（按实际缺失项生成，没有缺参时不显示这一行）

                                            [ 退出 ]      ← 主按钮在右下角
```

* 提示窗沿用 §11.2 的调色板（主背景 `#2b2d30`、正文 `#e4e6eb`、次要 `#a0a4ab`、
  警告 `#f5a623`、按钮 `#3a3d42`／悬停 `#45494f`／按下 `#2d5f8a`）与随包 MiSans，
  按钮在右下角；**Esc / 回车 / 关窗都等于点「退出」**；
* **降级链**：深色提示窗 → 系统原生 `messagebox`（深色窗建不起来时）→ stderr + 日志；
  任何一步失败都不许抛异常、不许卡住（宁可少一句提示，也不能让安装器挂在提示上）；
* 全过程**不触碰安装目录、不写状态文件、不写成功标记**；提示只做提示，
  不"自动修复"、不"找不到主程序就自己装"；
* 直接启动的日志写进 `TEMP/CACHE/MangaProof-update-installer/`（该目录存在时用），
  这样 §82「清理升级缓存」能一起清掉；目录不存在则**不创建**，退回系统临时根目录；
* 「主程序正在运行」的判定复用 §46 的进程名口径（`MangaProof`）；`ps` 查不了时
  **只记日志、不拦截**（与 §46 的保守哲学一致）；
* 本版**不做**：安装器自检自己的运行目录（§40 仍由主程序负责把安装器复制到临时
  目录运行；安装器保持"从哪运行都能跑"，避免影响单测、开发与排障）、父进程名校验
  （提权后父进程是 `consent.exe` / `pkexec` / `osascript`，必然误判）、调用凭证签名。
